# Harness account switching framework, topbar 1-click switcher, and forever-session continuity

## Background

The dashboard needs a unified framework for registering multiple account slots per harness, switching the active account cleanly from the topbar usage popover, and continuing long-lived sessions across account switches (such as when a weekly or 5-hour quota window is exhausted mid-task).

`261113-feat-ws-dashboard-harness-auth-slots` captured the initial Orca `(131)=a` direction for per-slot isolated config homes (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`) targeting new sessions only. It left open how existing forever-sessions preserve identity and conversation context across a switch, how the built-in `werk` harness switches accounts without restarting, and how the topbar usage popover stays compact alongside `/settings?section=account`. This ticket settles those decisions for backlog implementation without modifying `261113`.

## Decisions

- **D1 — Role-separated topbar UX (`(1772)=a`).** The `.usage-toggle` popover (`assets/usage.js`, `assets/usage.css`, `assets/dashboard-rail-popovers.js`) renders usage charts, per-harness active account slot 1-click switcher controls, and a shortcut link to `/settings?section=account`. Full credential onboarding and configuration—OAuth login, API key registration, background-usage consent prompts, voice keys, and local endpoints (`account_routes.go`, `WsSettingsAccount` in `assets/dashboard-settings-account.js`)—remain on `/settings?section=account`. This preserves the compact `261115-feat-ws-dashboard-settings-in-usage-strip` usage popover and `.tu` topbar strip readability.
  - *Rejected:* Embedding OAuth login, API-key forms, or consent banners inside `.usage-toggle`, which crowds the compact header bar.
- **D2 — Per-slot isolated `config_dir` + hybrid forever-session continuity on Stop+Restart (`(1773)=a`).**
  - **`werk` (`WerkBackend`, `wscred` `openai_store.go`):** `openAIState.Accounts` (`map[client_id]json.RawMessage`), `openAIState.Active`, and `openAIMu` already support multi-workspace SIWC registrations. Switching accounts updates the active (or session-pinned) `ClientID` in-process via a new `SetActiveOpenAIAccount` store method and `/api/account/*` route with **zero process restart**; any in-flight turn completes on its already-bound `ClientID`, and the next turn picks up the newly selected `ClientID`.
  - **External CLIs (`codex`, `claude`, `agy`):** Long-lived child processes managed by `wsholder` (`codex app-server`, `claude -p --input-format stream-json`, `agy acp`) cannot swap auth mid-process. Pure in-place swapping of shared default credential files is rejected because concurrent sessions/terminals overwrite rotating refresh tokens, prevent parallel multi-account runs, and amplify Windows AhnLab V3 / file-lock contention (`261113` Orca `(131)=a`). Instead, isolate per-slot `config_dir` values (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`, etc.) passed via `StartSpec.Env` and bound to the conversation via additive slot-affinity metadata on `wsagent.Record`.
  - **Stop+Restart continuity for an existing forever-session (`2a` -> `2b`):** When switching an active external-CLI forever-session to Slot B and performing Stop+Restart:
    1. **Path `2a` (primary when upstream permits):** Copy/migrate the session transcript (e.g., `CODEX_HOME/sessions/.../rollout-...-<id>.jsonl` or `CLAUDE_CONFIG_DIR/projects/.../<id>.jsonl`) into Slot B's `config_dir` and attempt native `--resume` / `thread/resume` using `Record.SessionID`. For `codex`, run a **pre-flight auth check** on the target slot (`account/read`, or an `auth.json` presence/validity check) before relying on `thread/resume`, because the Phase 1 spike showed `thread/resume` succeeds locally even with a missing/corrupt `auth.json` or a mismatched `creator_account_id` (see `## Spike Findings`).
    2. **Path `2b` (automatic fallback on upstream cross-account resume refusal):** Rotate cleanly through `rotateExternalSession` (`agents-plugin-tool/internal/wsagent/compaction.go`, search `func (.*) rotateExternalSession`), clearing `Record.SessionID` / `Record.SessionFile` and starting a fresh native thread on Slot B with `<ws-restore>` checkpoint handoff inside the **exact same permanent `ws` session** (`Record.ReplyID`, `Record.WSKey`, dashboard ring history, and worktree preserved). For `codex`, the `2a` -> `2b` fallback triggers on any of: pre-flight auth-check failure, `thread/resume` failure, **or** a post-resume `turn/start` rejection (`unauthorized` / session rejection), because a real Account A -> B server-side rejection surfaces only at `turn/start` and could not be tested locally with a single Codex account.
- **D3 — Two-stage incremental rollout (`(1774)=a`).**
  - **Stage 1 (Phases 1–2):** Shared account slot registry + topbar 1-click switcher UI + **`werk`** (OpenAI SIWC multi-account zero-restart switching + OpenRouter) + **`codex`** (`CODEX_HOME` per-slot isolation, fixing global `os.Getenv("CODEX_HOME")` reads such as `codex_choices.go`, plus the empirical cross-account `thread/resume` spike determining `2a` vs `2b`).
  - **Stage 2 (Phase 3):** Empirical Windows CLI spike for **`claude`** (verify whether Windows Claude CLI stores OAuth strictly under `%CLAUDE_CONFIG_DIR%\.credentials.json` vs `.claude.json` or Windows Credential Manager, and whether cross-account `--resume` works) and **`agy`** (verify Windows auth storage and whether `--gemini-dir` isolates auth cleanly while strictly respecting the ToS ban on extracting third-party OAuth or Keychain tokens from `261119`/`261122`), then integrate both into the shared slot framework.
- **D4 — Capture to `todo/` backlog (`(1782)=a`).** Scope this design as an actionable `todo/` feature ticket rather than immediate in-flight release work.
- **D5 — Compatibility Tier T0 (transparent).** Additive slot-affinity fields on `wsagent.Record` / `LeadOptions`, additive active-slot / account-list fields on `/api/account/status`, and additive topbar switch endpoints preserve wire and on-disk compatibility: older daemons keep unknown JSON fields on `Record` intact and older clients ignore extra status fields without error.
- **D6 — Queued account switch applied at compaction / `/clear` boundary via forced process cold-restart (`(1798)=a`).**
  - **Deferred non-disruptive queuing:** Add an additive T0 field (`pending_account_slot` / `PendingAccountSlotID` on `wsagent.Record` / `conv` in `agents-plugin-tool/internal/wsagent/record.go`) so a user can queue an account slot switch without interrupting an in-flight turn, taking effect at the next compaction or `/clear` boundary.
  - **No process reuse when a queued switch is pending (per-harness lifecycle):**
    - **`ws` compaction mode (`rotateExternalSession`, `agents-plugin-tool/internal/wsagent/compaction.go:998-1100`):** Already tears down and respawns external CLI processes (`claude`, per-conversation `codex app-server`, `agy`) via `retireCompactionProcess()` (`compaction.go:1114`, `func (c *conv) retireCompactionProcess`) -> `startLead` / `startWorker` (`runner_lead_start.go:21`, `runner_process.go:140`). Committing the queued slot between teardown and respawn applies the new slot env (`CLAUDE_CONFIG_DIR`, `CODEX_HOME`, etc.) with zero extra restarts.
    - **`native` compaction mode & manual `/clear`:** Both `native` compaction (`compaction.lead_mode=native` / `compaction.worker_mode=native`, `compactIdle()` -> `/compact` or `thread/compact/start`) and manual `/clear` (`kickInput()` in `agents-plugin-tool/internal/wsagent/runner_conv.go:2018`, `func (c *conv) kickInput`; `/clear` is a queued `wsinbox.Command` (`Name: "clear"`, built from `rec.Entry.Command` in `kickInput`), not a Go string literal, and non-`compact` commands go to the process's `RunCommand`) currently reuse the running `c.proc` and would keep stale account env/credentials. When `PendingAccountSlotID` is set, explicitly block process reuse at `compactIdle()` / `postCompact` (`compaction.go:685` onward, `func (c *conv) compactIdle`, even in `native` mode) and when intercepting `/clear` in `kickInput()`, forcing cold teardown + fresh respawn (`retireCompactionProcess()` -> commit queued slot -> `startLead` / `startWorker` with new slot env + `<ws-restore>`). Place this hook in `compactIdle()` / `postCompact` and `/clear` handling, **not** `restartIfDue()` (`agents-plugin-tool/internal/wsagent/runner_recovery.go:262-267`, which returns `false` while `compactPending != nil || compactResume`).
    - **Mid-turn native auto-compaction & `resume=false` workers:** Never tear down mid-turn during Claude's internal native auto-compaction (`CompactStart` / `CompactEnd` in `compaction.go:1343-1361` before `TurnEnd`); wait for `endTurn` (`runner_events.go:381`) -> `compactIdle()`. For workers completing natural turn-end auto-hard compaction (`resume=false`), commit the pending slot before idle stop so the next wake spawns with the new slot's env.
    - **`werk` (`ProcessDurable`, `agents-plugin-tool/internal/wsagent/werk_loop.go:72-80`):** In-daemon goroutine resolves `Token` / `PlanToken` per model request (`providerToken` / `BeginOpenAIPlanRequest`), so flipping the active (or queued) slot applies cleanly with no process teardown.
- **D7 (1803) — `werk` in-flight guarantee via a turn-bound `ClientID` pin (technical, auto-confirmed).** The current store keeps one in-memory `openAIAccount`, `BeginOpenAIPlanRequest` captures the then-active account per call, and `openAICurrentLocked` returns `ErrNotConfigured` for a request pinned to a non-active account. Per-request resolution alone therefore lets later model requests of an in-progress tool loop pick up the new account or fail. `werkLoop` carries a **turn-bound `ClientID` pin** taken at turn start and used for every model request of that turn, and the store gains a path that serves a registered non-active account (refresh, consent, and plan checks included). `SetActiveOpenAIAccount` updates `s.openAIAccount` and `doc.Active` together and persists both. The next turn pins the newly active `ClientID`.
  - *Rejected:* Pure per-request resolution (breaks the in-flight guarantee).
- **D8 (1804) — `SetActiveOpenAIAccount` refuses an unusable target (technical, auto-confirmed).** A target that is not registered, lacks tokens, lacks plan scope, or lacks consent is refused at switch time with a fixed error code and no state change; it never succeeds and then fails on the next request. No raw credential appears in the error.
  - *Rejected:* Accept the switch and surface the failure on the next request (a silent broken active account).
- **D9 (1805) — OpenRouter stays single-key, outside the slot framework (technical, auto-confirmed).** The store holds one OpenRouter key; Stage 1 slots cover OpenAI SIWC (`werk`) and `codex` only. The D3 mention of OpenRouter means it keeps working beside the switcher, with no OpenRouter slots.
- **D10 (1806) — Slot-aware home resolver precedence and ownership (technical, auto-confirmed).** Phase 1 owns a single slot-aware home resolver for `CODEX_HOME` / `CLAUDE_CONFIG_DIR`. It preserves the existing precedence that an explicit `DaemonOptions.Home` suppresses inherited `CLAUDE_CONFIG_DIR` / `CODEX_HOME` roots (commit `075fa3ff`), then slot `config_dir`, then the inherited environment, then the default home. `261127-feat-ws-werk-usage-metrics-and-openai-codex-unification` Phase 4 consumes this resolver for its Codex CLI account-ID read when it has landed; otherwise that read is default-home only and its card says so (soft ordering, no `blocked-by:`).
- **D11 (1807) — Registry state and switch UX details (technical, auto-confirmed).** The slot registry lives in a separate daemon state file written with the same atomic-write and Windows User-SID DACL discipline as `wscred` Type 5, and holds no tokens (slot ID, harness, label, `config_dir`, active flag); an in-memory copy serves `/api/account/status` and SSE. A "guided Stop+Restart" is a confirmation step in the popover that offers "switch now (Stop+Restart)" or "switch at next compaction or `/clear`" for the selected conversation, shows the queued slot on the conversation until it applies, and uses fixed error codes.
- **D12 (1808) — Account/slot dimension on usage rows (technical, auto-confirmed).** Per-model usage rows recorded by `261127-feat-ws-werk-usage-metrics-and-openai-codex-unification` Phase 2 carry an additive optional account/slot key so a switch never mixes spend from different OpenAI accounts in one aggregate; the Werk (OpenAI) card identity and masked label follow the active (or turn-pinned) account via the existing SSE path.

- **D13 (1799) — Topbar switch sets the harness default and queues live conversations (`(1799)=b`).** For hosted external-CLI harnesses (`codex`, later `claude`/`agy`), a topbar 1-click switch sets the harness default slot for new sessions **and** queues `PendingAccountSlotID` on every live conversation of that harness (applied at the next compaction or `/clear` boundary per D6). Each live conversation still offers its own "switch now (Stop+Restart)" or "at next compaction or `/clear`" action (D11). `werk` keeps its instant global switch with the D7 turn-bound pin. Fan-out rules (technical): a conversation already on the target slot is skipped; a pending slot already queued on a conversation is overwritten (last write wins); non-lead worker conversations of that harness are included. The Codex CLI usage card follows the harness default slot through the D10 resolver, probes that one slot (no per-slot fan-out), and does not imply that every running conversation already uses that account.
  - *Rejected:* New-sessions-only default (live sessions never follow the click); focused-conversation-only application.
- **D14 (1800) — Codex slot provisioning (`(1800)=a`).** The daemon allocates `<ws data dir>/slots/codex/<slot-id>/` (owner-only permissions; Windows User-SID DACL) and `/settings?section=account` runs `codex login` with `CODEX_HOME` pointed at that directory. A user-supplied existing `CODEX_HOME` directory stays supported as an advanced path. The slot directory is registered in `deniedBasePaths`, and the settings controls ship with `en`/`ko` and the other shipped-locale strings (Phase 2).
  - Mechanics (technical): an existing default-home login appears in the registry as an implicit slot with no `config_dir` (the D10 fallback), so switching away from it and back is possible. The daemon-run `codex login` surfaces its auth URL to the settings UI, detects completion by the slot's `auth.json` appearing and passing the `account/read` pre-flight, and has a bounded timeout and a user cancel that kills the process tree and leaves no half-provisioned slot in the registry.
  - Terminology: registry and API types say "account slot" explicitly, because `HostedSlot` / "slot" already names the live UI sink in `wsagent` and `wsdashboard`.
  - *Rejected:* Seeding by copying the default home's `auth.json` (recreates the shared rotating-refresh-token problem that motivated per-slot isolation).
- **D15 (1801) — `agy` stays single-slot if no ToS-compliant isolation exists (`(1801)=a`).** `agy` is shown read-only (non-switchable) in the switcher and Phase 3 closes with the spike outcome recorded in `### Result`; no keychain or third-party token extraction.
  - *Rejected:* Dropping `agy` from the phase; shipping an `agy` switcher that implies isolation that does not exist.
- **D16 (1802) — No user-facing session-level `ClientID` pinning for `werk` (`(1802)=a`).** The global active account plus the internal turn-bound pin (D7) is the whole scope; a session-level pin can be added later as an additive T0 field.
  - *Rejected:* A session pin that survives global switches (undefined interaction with `pending_account_slot`).
- **D17 (1813) — `agy` single-account login trigger in Phase 3 (`(1813)=a`).** Audit ground truth: the `agy` CLI has no `login` / `logout` / `auth` subcommand; when unauthenticated or expired it emits an auth URL on stderr, and `internal/wsdashboard/plan_usage_agy.go` (search `agyAuthHold`) sets a daemon-lifetime `agyAuthHold` latch that today requires a daemon restart to clear. Phase 3 adds to `/settings?section=account` an `agy` auth status plus an action that opens the auth URL in the browser when unauthenticated or expired, clears the `agyAuthHold` latch, and triggers a re-verify probe; the exact CLI trigger behavior is verified in the Phase 3 spike. This stays single-account: no multi-account switching and no keychain or third-party token extraction (D15).
  - **Supersedes `261119-feat-ws-agy-plan-usage-display` D13 (1409) in part (owner-confirmed `(1813)=a`):** that decision said the auth-required hold clears only on daemon restart and rejected clearing it on popover open. The contract becomes "restart, or an explicit settings re-auth action". Clearing on popover open stays rejected, the billed-turn latch (`agyBilledLatch`) is unchanged, and the explicit settings click is a deliberate user action rather than a passive read, which preserves the original rationale.

- **D18 (1814) — Every account sign-in supports direct local login AND remote / cross-device login (owner-confirmed).** For all four harnesses (`werk`, `codex`, `claude`, `agy`), each `/settings?section=account` sign-in flow supports both: (1) **direct local login** that opens the auth URL in the local browser (`d.openSystem`) and completes automatically; and (2) **remote login**: always show a copyable auth URL with a Copy button plus a paste-code / paste-callback-URL input and Submit control, so the user can sign in on another PC or phone and paste the result back. A failed or skipped local browser launch never aborts the pending sign-in with `browser_unavailable`; the attempt stays `waiting`. Remote login does not relax the existing access policy: the settings UI and its routes stay behind `localViewer` + `sameOrigin` (+ `loopbackPeer` where already applied); the user copies the link from the local dashboard and pastes the result back into the same dashboard. Per-harness mechanics (each phase's spike verifies the exact CLI wire behavior it depends on):
  - **`werk` (OpenAI SIWC, Phase 2; `wscred/openai_oauth.go`, `wsdashboard/account_signin.go`, `account_routes.go`, `assets/dashboard-settings-account.js`):** today `openAIOAuth.browserCode` listens on `127.0.0.1:0`, hides `authorizeURL` behind a one-time `/auth/start/<token>`, and `accountSignIn.run` fails with `browser_unavailable` when `openBrowser` errors; `accountSignInStatus` carries no `authorize_url`. Required: expose a copyable `authorize_url` in `accountSignInStatus` (`Cache-Control: no-store`, `localViewer` + `sameOrigin`), **omitting `id_token_hint`** from any copyable URL so the prior `id_token` is never leaked, keeping `/auth/start/<token>` for the local open so `argv` stays clean; keep the attempt `waiting` when `openBrowser` fails or copy-link mode was chosen; add `POST /api/account/sign-in/complete` (`localViewer` + `sameOrigin` + `crossSiteFetch`, bounded `accountBody`, `Cache-Control: no-store`, matching the active attempt) feeding the same `callbackOnce`-guarded completion channel as `/auth/callback`. It accepts a full pasted redirect callback URL (`http://127.0.0.1:<port>/auth/callback?code=...&state=...&client_id=...`) validated with `subtle.ConstantTimeCompare` on `state` and `parseOpenAICallback`, or a raw `code` when the `clientID` is not the dynamic one. For a fresh `dynamic_agent_client` registration `parseOpenAICallback` requires `client_id` from the redirect query, so the UI guides pasting the full redirect URL and a missing `client_id` returns a fixed error code. Never log or echo the raw `code`, `code_verifier`, `id_token_hint`, or tokens. The Sign In control currently disables itself when `!nav.status.loopback_peer` (`dashboard-settings-account.js`); keep that loopback policy intact.
  - **`codex` (Phase 2, per-slot `CODEX_HOME` per D14):** support both a local browser OAuth `codex login` flow, with a copyable auth URL and an SSRF-safe pasted-callback replay (the pasted URL's host must be `127.0.0.1` / `localhost` and its port must match the active `codex login` process's own `redirect_uri` listener port before it is forwarded), and the built-in device-code flow (`codex login --device-auth`, present in `codex login --help`) that shows a copyable verification URL and a copyable one-time user code for zero-callback login on another device.
  - **`claude` (Phase 3, `claude auth login`):** support both the local browser open and copying the printed OAuth URL with a paste-back of the auth code or callback URL (delivered to `claude auth login` stdin or a validated localhost callback listener; the Phase 3 spike verifies the exact wire behavior).
  - **`agy` (Phase 3, D17 single-slot):** the Phase 3 spike launches `agy` with an open stdin pipe, extracts the auth URL from its `Authentication required. Please visit the URL ...` output (the prior adapter spike saw `agy` print a login URL and exit when stdin was `/dev/null`), and presents **Open in browser**, **Copy link**, and **Paste login code / callback URL** (the pasted code is written to stdin without logging it, or the callback is completed), then clears `agyAuthHold` / `agyStatus` so usage polling resumes without a daemon restart. Single-slot per D15; no keychain or third-party token extraction.
  - **Unsupported mode outcome (technical):** if a Phase 3 spike shows a harness (most likely `agy`, whose prior adapter spike saw it print the URL and exit on closed stdin) cannot support one of the two modes, that harness ships with the supported mode only, and the gap is recorded in `### Result` rather than blocking the phase. The sign-in wire checks join Phase 3 step 1 so they run before step 2 relies on them.
  - **`browser_unavailable` (technical):** the `werk` change means a failed browser launch no longer sets `browser_unavailable` there; update the existing tests that assert that failure, and drop or keep the i18n key in every locale table depending on whether another path still sets it.
  - **Security (all harnesses):** pasted codes, callback URLs, and auth URLs are bounded in size, never logged or echoed in status payloads after completion, and never persisted outside the harness's own credential store; auth URLs returned to the UI carry `Cache-Control: no-store`.

## Spike Findings

Empirical `codex` spike (`codex-cli 0.170.0`, macOS, one Codex account; owner confirmed `(36)=a` to fold these into the ticket and proceed without blocking on a live second-account re-login):

- Same-account isolated `CODEX_HOME` + `thread/resume` works when only `auth.json` and `sessions/YYYY/MM/DD/rollout-...-<id>.jsonl` are copied into the fresh home; `state_5.sqlite` and `config.toml` are not needed. `initialize.codexHome` matches the isolated path exactly, `thread/list` returns count=1, and `account/read` returns `type: "chatgpt"` with `email` / `planType` / `workspaceName`.
- The rollout's `session_meta` embeds `account_scoped: true`, `creator_account_id`, `creator_user_id`, `cwd`, and `runtime_workspace_roots`; it does not embed `codex_home`.
- `thread/resume` succeeds locally even with a missing/corrupt `auth.json` or a mismatched `creator_account_id`, so it is not evidence of cross-account acceptance. Hence the pre-flight auth check and the `turn/start`-time `2a` -> `2b` trigger (D2).
- Not tested (needs a second Codex account): a real Account A -> B server-side rejection signature.
