# Shared Dashboard Control MCP API (`ws/daemon.*`), Multi-Tab WebSocket Bridge, and Top-Level Shell 1-Click Confirmation Banner

## Background

Dashboard-hosted coordinator and opted-in lead sessions currently lack a unified, safe, browser-and-desktop-compatible surface to inspect live daemon state, discover open dashboard tabs, inspect the active semantic DOM, drive allowlisted UI navigation/controls, or capture visual state without exposing remote debug ports or arbitrary script evaluation.

## Decisions

- **`(1745)=a` — Shared opt-in MCP layer & per-session gating (`T0` transparent):**
  - **Chosen:** Expose `ws/daemon.curl`, `ws/daemon.tabs`, `ws/daemon.dom`, `ws/daemon.ui`, and `ws/daemon.screenshot` as a shared dashboard-control MCP layer.
  - **Default posture & persistence:** Regular hosted leads default to **OFF** (omitted from `tools/list` and `agy` `DirectTools` unless opted in per session). Opt-in mirrors peer ticket `261128-feat-conv-history-mcp-api-and-session-permission-toggle`:
    - `wsagent.Record.DashboardControlAccess bool` (`json:"dashboard_control_access,omitempty"`) stored only in `wsagent.Record` (never `wsdashboard.Registration`).
    - `State` / `GET /agents/<id>` exposes `dashboard_control_access` (persisted) and `dashboard_control_access_effective` (snapshot at MCP token attach; equals persisted when stopped).
    - Toggle route: see `(1752)`; the `decodePermissionRequest` allowlist is NOT extended because those routes require a `permission_level` selection.
    - Dynamic merge into `tools/list` and `agy` `DirectTools` when opted in; immediate server-side call denial on revocation without killing the running process; inline restart badge + "Stop now" button in the existing-session popover (`dashboard-leads.js`) and new-session modal (`dashboard-new-session.js`, which already exists on `develop` together with `dashboard-new-session.css`; `dashboard-leads.js` has no new-session references, so no fallback path is needed) whenever `running && dashboard_control_access !== dashboard_control_access_effective`. The peer ticket `261128-feat-conv-history-mcp-api-and-session-permission-toggle` lives on a parallel branch and is not visible in this checkout; the `related:` link is kept and its tracking advisory is expected.
  - **Caller scope:** Dedicated Companion Tier-2 (`companion-work` marker from `261127-feat-ws-companion-layered-agents-and-naming`) receives auto-access (wired in `261127` Phase 2, keeping this ticket independently testable via opted-in regular leads). Worker subagents, Tier-1 `companion-body`, and remote/untrusted viewers are strictly blocked.
  - **Ownership over `261127`:** This ticket is the single owner of the `ws/daemon.{curl,tabs,dom,ui,screenshot}` tools and their design (per-session opt-in, WebSocket push + HTTP POST reply bridge, top-level shell 1-Click banner), as the owner settled `(1745)=a`. `261127` Phase 2 and its `(1728)`/`(1729)` bridge design (bearer-authenticated curl, SSE-to-POST bridge, in-messenger gate) are superseded wherever they overlap and shrink to consuming the `companion-work` auto-access wiring; amending `261127` is a separate follow-up outside this ticket's edit scope.
  - **Rejected:** Exposing `ws/daemon.*` unconditionally to all hosted leads, storing the opt-in on `wsdashboard.Registration`, allowing worker subagents access, or building a second parallel `ws/daemon.*` implementation inside `261127`.

- **`(1728)=a` & `(1742)` — Shared top-level `shell` 1-Click Confirmation Gate:**
  - **Chosen:** Server-side fail-closed classification (never model-judged):
    - **Immediate (no confirmation):** `GET` and `HEAD` calls on `ws/daemon.curl`, plus `ws/daemon.tabs`, `ws/daemon.dom`, `ws/daemon.screenshot`, and non-destructive navigation/focus `ws/daemon.ui` actions (`navigate`, `focus_session`, `open_settings`, `select_panel`).
    - **Confirmation-gated:** All other `ws/daemon.curl` HTTP methods (`POST`, `PUT`, `PATCH`, `DELETE`, etc.) and mutating `ws/daemon.ui` actions (`click_ref`, `fill_ref`) block up to `120s` behind a non-blocking **top-level `shell` 1-Click approval banner/toast** (in a dedicated shell slot that never collides with `data-openai-consent` / `.account-banner` / `:root[data-account-banner]`), returning `denied` on reject, timeout, or dismiss, one-shot bound to `request_id`.
  - **Rejected:** Model-judged confirmation, blocking modal dialogs that freeze the shell, or sharing/overwriting the `data-openai-consent` DOM node.

- **`(1746)=a` — Semantic-first DOM/UI control, stable refs, and multi-tab targeting over existing WebSocket:**
  - **Chosen:**
    - **Transport:** Reuse the existing `openStream` WebSocket (`/rail/events`) with zero new SSE/WS connections. Daemon -> tab requests travel as server-push `daemon-bridge-request` events; tabs send only tiny focus heartbeats (`tab_id`, `visibilityState`, `lastFocusedAt`, active `/s/<rid>`) over WS within `wsMaxFrame = 1 << 10` (1 KiB). Larger bridge responses post to `POST /api/daemon/bridge-reply` (`TrustedWrite`, correlated by `request_id` + single-use nonce/token, strictly rejecting stale, replayed, or foreign IDs). Remain compatible with peer `conv-reveal` WS event `{replyId, entryId?, focus?, reason?}` and `/s/<rid>#entry=<key>`.
    - **`ws/daemon.tabs`:** Returns connected dashboard tabs (`tab_id`, `visible`, `last_focused_at`, `active_route`, `active_reply_id`, `capabilities` such as native Tauri vs browser).
    - **Default target selection:** Active control tools (`ws/daemon.dom`, `ws/daemon.ui`, `ws/daemon.screenshot`) target the **most recently focused visible tab** by default, or an explicit `tab_id` parameter; return structured error `no_active_tab` when none is available.
    - **`ws/daemon.dom`:** Returns a bounded structured semantic/a11y snapshot (stable `data-ws-*` attributes / assigned ephemeral `ref` handles, active route/frame/modal state, hard byte and node caps, and mandatory masking of sensitive inputs such as `type="password"`, API keys/tokens, and secret inputs).
    - **`ws/daemon.ui`:** Allowlisted semantic actions ONLY (`navigate`, `focus_session`, `open_settings`, `select_panel`, `click_ref`, `fill_ref`), routed through `shell.js` `KINDS` + origin-checked `postMessage` when targeting a framed session. Zero arbitrary JS `eval` or arbitrary script execution.
  - **Rejected:** Opening a second SSE/WS channel, raising `wsMaxFrame` to push large DOM/image payloads over WS, raw CSS-selector injection, or arbitrary `eval`.

- **`(1747)=a` — Honest staged fallback for `ws/daemon.screenshot`:**
  - **Chosen:**
    - **Tier A (Native WebView):** Native WebView capture in `desktop/src/` when the target tab reports Tauri/desktop native capability (following the top-frame, origin-pinned bridge pattern of `notify-bridge.js` / `notify.rs`).
    - **Tier B (Headless Playwright):** Local headless Playwright route-reproduction capture reusing the cached Playwright / `WS_PLAYWRIGHT_MODULE` seam where configured/available, returning a worktree-scoped temp PNG path or bounded image metadata without touching live user cookies or secrets.
    - **Tier C (Honest fallback):** Standard browser tabs without native capture MUST NEVER use `html2canvas` or SVG `foreignObject` hacks (which break on cross-frame iframes and WebGL VRM `preserveDrawingBuffer`); return an honest structured response (`mode: "dom_fallback"`, `reason`, plus the bounded `ws/daemon.dom` semantic snapshot).
  - **Rejected:** `html2canvas` / SVG `foreignObject` DOM-to-canvas hacks, or attaching remote CDP debugging ports.

- **`(1752)` [technical, auto-confirmed after review] — Opt-in toggle route:** a dedicated strict-decoded route `POST /agents/<id>/settings/dashboard-control` with body `{"dashboard_control_access": bool}` (user-only via the same trusted-viewer gate as the permission raise), plus the same field accepted by the create-session request the new-session modal posts (added to that request's strict per-route field list where it decodes strictly). The toggle control sits in the existing-session popover and the new-session modal next to the permission-level control, and is hidden or disabled where only a legacy non-strict route is available, since that route would drop the field silently. Reason: on `develop`, `/agents/leads/permission` and `/agents/<id>/settings/permission` unconditionally call `body.selection()`, which 400s without a valid `permission_level` and otherwise writes an explicit permission selection that would break the legacy-derived `auto` contract of `261115-feat-ws-permission-profile`; the legacy non-strict routes would silently drop the field. Phase 1 starts by checking whether the peer `261128-feat-conv-history-mcp-api-and-session-permission-toggle` has landed a lone-toggle route; if it has, reuse that route shape instead of adding a second one. Rejected: allowlist entry on the permission routes (breaks the `permission_level` contract), making `permission_level` optional there (contradicts the ready permission-profile ticket).
- **`(1753)` [technical, auto-confirmed after review] — `ws/daemon.curl` contract:**
  - Target: the daemon's own loopback origin only. The tool takes `method`, a daemon-relative `path` (starting with `/`, no scheme, host, userinfo, or `..` segments after normalization), optional `query`, optional JSON/text `body` (POST-class only; a GET/HEAD with a body is rejected), and optional `Accept`/`Content-Type` headers only. Any other header, including method-override headers and `Origin`/`Cookie`/`Authorization`, is rejected; the server sets origin and authenticates in-process as the local trusted viewer without exposing the credential to the model.
  - Caps: request body 256 KiB, response body 512 KiB (truncated with `truncated: true`), 30 s request timeout excluding the confirmation wait.
  - Response: `{status, headers (content-type only), body, truncated}`.
  - Denied for every method (`forbidden_path`): `POST /api/daemon/bridge-reply` itself and every route family that renders or returns a credential: the `/settings` page (LAN token via `lanAccessFor`), `/auth/cookie`, `/auth/link`, `/auth/exchange`, `/auth/clipboard`, the credential-token and credential/endpoint-change routes, and `/shutdown` (enumerated against the access-exempt route list in `localhost_auth.go`, with a test that fails when a new exempt route is not classified). All responses additionally pass a credential-redaction filter (LAN token query values, bearer-shaped tokens) before reaching the model; the same redaction applies to `ws/daemon.dom` link text and URL values.
  - Classification by the verb actually sent, after normalization: only `GET`/`HEAD` are immediate; everything else is gated.
  - Rejected: arbitrary-host proxying, model-settable auth headers, bearer-authenticated curl (superseded `261127` design).
- **`(1754)` [technical, auto-confirmed after review] — Bridge and 1-Click confirmation protocol:**
  - Tab registry admission: only `/rail/events` streams whose viewer is `localViewer`; LAN or remote streams are never registered or targeted. The shell stream opts into the heartbeat explicitly (the visibility-frame hook exists today only for opted-in streams).
  - Banner target: the same default target as the control tools (most recently focused visible local tab, or explicit `tab_id`). The banner renders only in that tab. No eligible tab means immediate `denied` with reason `no_active_tab`, never a 120 s wait.
  - Delivery and answer: the daemon pushes a `daemon-confirm-request` WS event carrying `request_id`, one-shot nonce, and a summary (method and path for `ws/daemon.curl`; ref accessible name, action, and fill value for `ws/daemon.ui`); the user's approve/deny/dismiss posts to `POST /api/daemon/bridge-reply` (`decision` field) with the same `TrustedWrite` and nonce rules, so there is one reply route. Timeout, tab disconnect, or dismiss resolves `denied`; a late reply is rejected as stale.
  - Anti-self-approval: the banner's controls are excluded from `ws/daemon.dom` snapshots and ref assignment, and approve/deny act only on trusted user events (`event.isTrusted`), so a synthetic click delivered through `ws/daemon.ui` `click_ref` cannot answer a pending request.
  - Phase layout consequence: the push channel, tab registry, focus targeting, and `bridge-reply` route are foundations needed by the banner, so they ship in Phase 1; Phase 2 builds `tabs`/`dom`/`ui` on them.
- **`(1755)` [technical, auto-confirmed after review] — Screenshot tier selection and return contract:**
  - Selection order for the target tab: Tier A when it reports native capture capability; else Tier B only when a Playwright module is configured at runtime and the daemon can mint a short-lived loopback-only credential for the headless context; else Tier C. Tier B degrading to Tier C is the normal fallback, not an error.
  - `WS_PLAYWRIGHT_MODULE` is test-only on `develop`; Tier B introduces its own optional runtime configuration and ships no Playwright dependency.
  - Tier B is a fresh render of the target route, not the live UI (no open modals or typed input). The response labels it `mode: "route_render"`, `live: false`. Tier A is labeled `mode: "native"`, `live: true`. Tier C is `mode: "dom_fallback"`, `reason: "screenshot_unavailable"`, plus the `ws/daemon.dom` snapshot.
  - Return shape: PNG written under the daemon's per-session cache directory (no caller-worktree assumption) with `{path, width, height, bytes}` metadata; Tier A bytes arrive via `POST /api/daemon/bridge-reply` and are stored the same way. Image bytes are never inlined in the MCP result. The `bridge-reply` body cap for image bytes is 8 MiB; larger captures yield `payload_too_large`.
- **`(1756)` [technical, auto-confirmed after review] — Schema pins:** `ws/daemon.dom` snapshot caps 64 KiB and 1500 nodes (`truncated: true` when exceeded). `ref` handles are valid only within the snapshot generation that issued them and are invalidated by the next snapshot or any navigation; using one yields `stale_ref`. Error codes: `no_active_tab`, `tab_gone`, `stale_ref`, `ref_not_found`, `denied`, `timeout`, `forbidden_path`, `payload_too_large`, `screenshot_unavailable`. Server-side tool denial requires `persisted && effective`, so a grant made after attach stays denied until restart. The tools are added to `isLeadOnlyTool` / `sessionToolAccess`, pass through `companionPostureRefusal` (hands-busy lock), and every new dashboard string is added to all 11 locale tables.

- **Compatibility Tier Verdict — `T0` (Transparent):**
  - `wsagent.Record` (`agents-plugin-tool/internal/wsagent/record.go#L31-L245,L244-L302`) retains unknown top-level JSON keys via `unknown map[string]json.RawMessage`, so an older binary reading and rewriting a record with `dashboard_control_access: true` preserves the field; reopening with the new binary recovers the persisted setting without data loss (`wsdashboard.Registration` in `registry.go#L79-L146,L269-L357` drops unknown fields and is NOT used).
  - Regular leads default to `dashboard_control_access: false` (`omitempty`), preserving existing `tools/list`, `agy` `DirectTools`, and `openStream` behavior unchanged.
  - Older browsers ignore unknown server-push WS events (`daemon-bridge-request`, `daemon-confirm-request`), and the existing `visibility` frame handler in `stream_ws.go#L53-L78,L121-L142` ignores unknown additive heartbeat keys cleanly within `wsMaxFrame = 1 << 10`.
  - `ws/daemon.*` tools are additive entries in `mcp/server_inventory.go`, `mcp/server_schemas.go`, `agents-plugin/runtime.json`, and `agents-plugin-wsflow/runtime.json`.
