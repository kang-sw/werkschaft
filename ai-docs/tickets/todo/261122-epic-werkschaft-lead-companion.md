# Werkschaft App-Scoped Lead Companion (Desktop Pet)

## Scope

Deliver the opt-in **Werkschaft Lead Companion (desktop pet)** feature as a modular, pack-driven visual companion mounted once on the persistent Werkschaft dashboard outer shell (`dashboard.tmpl` / `shell.js`), defaulting strictly to **`off`**:

- **T0 opt-in configuration & live settings UI:** Scalar `dashboard.companion_*` keys mirrored across `ws` and `wsflow`, inspectable in Dashboard Settings, and broadcast live to the shell without page reloads.
- **Memory-first embedded & BYO pack serving (`performance.md`):** Serve an IP-clean embedded default pack alongside user-supplied local packs under `<config-home>/companions/<pack-id>/pack.json` with zero per-frame or per-request disk I/O.
- **App-scoped shell overlay & data-driven v3.1 Doll-Maker Canvas engine:** Persist one companion instance across session switches, anchor by default on the left session rail bottom divider (above `.rws-unreg` / `.rfoot`) so dense session panes stay unobstructed, subscribe to a lightweight active-view context/landmark relay from the active session iframe, and run a 3-layer extensible architecture: fixed low-level primitives (generic part/joint anchored `oscillate`/`keyframes`/`frames` tracks, whole-body stage physics, and prop trajectories), open `pack.json` asset dictionaries (`poses`, `gestures`, `expressions`, `props`, `fx` with `fallback` chains), and a declarative `scenarios` registry seeded with 12 built-in starter scenarios.
- **Optional agent director:** A lead-unaware lightweight sidecar that reads the visible session's recent activity and drives the companion in its pack persona's voice, kept strictly separate from the 0-token rules engine; settings split into a panel toggle plus a gear-opened floating modal.
- **Official ship art polish gate:** Decouple final art refinement from engine delivery so official shipped art passes explicit human visual sign-off against the v3.1 craft gates.

## Non-Scope

- Enabling the companion by default for any user or package (`ws` and `wsflow` both default `dashboard.companion_enabled` to `false`).
- Side-view walking articulation (`W. Side-Walk`) or bare-skin knee/hip joint cuts in v1/v3.1.
- Shipping any third-party or community character assets inside the public repository.
- Modifying agent orchestration, ticket workflows, or session lifecycle semantics based on companion state.

## Cross-Child Decisions

- **Pure-VRM track alongside 2D compatibility (`261126-research-ws-companion-hybrid-vrm-bust-spike`, owner 2026-11-26, (10)=a, (11)=a, (12)=a, (13)=a, (14)=c^GO):**
  - *Coexistence & T1 boundary (`release-compatibility.md`):* Existing `ws-companion/v1` 2D packs remain supported and untouched. VRM packs use `"schema": "ws-companion-vrm/v1"` under `<config-home>/companions/<id>/`; older daemons skip unknown schemas read-only and fall back to rendering `"default"` without overwriting `dashboard.companion_pack` (T1 display-degraded, patch-safe).
  - *Ecosystem & distribution boundary:* Customization uses external free VRoid Studio (+ BOOTH) -> single-file `.vrm` drop-in. The Go binary embeds only the lightweight lazy-loaded 3D runtime (~243 KiB gzip) and procedural IK/motion logic; the 1 official `.vrm` model (plus optional editable `.vroid` source link) is distributed externally as an opt-in download via the existing `companion_sources` official registry, never embedded in the binary.
  - *Shared behavior backbone:* Existing outer-shell overlay mount, `dashboard-companion-relay.js`, `companion_director.go`, `dashboard-companion-scenarios.js`, `builtins.js`, 2D `fx` badges, and normalized `gaze` pipeline remain the single event/scenario engine for both 2D and VRM renderers.
  - *VRM bust presentation & idle budget:* Default VRM framing is a bottom-right docked upper-body bust (`~240×280`, resizable) with `Digital Dissolve` lower-edge transparency, horizontal bottom-edge avoidance slide when interacting with right-side panels (`#bgal`/`#bcol`/`#drawer`), and adaptive `30/6/0` FPS throttling with `dpr <= 2` and zero WebGL creation when disabled or on 2D packs.

- **Rigging contract authority:** `ai-docs/manuals/companion-pet-rigging.md` is the canonical v3.1 Doll-Maker schema and craft-gate reference across all children.
- **3-layer data-driven extensibility (`ws-companion/v1`, no closed asset or scenario enums):**
  - *Engine fixed layer:* Only low-level compositing modes (with smart defaults/mode inference), generic part/joint anchored 2D tracks (`oscillate`, `keyframes`, `frames` around `pivot` + reusable `motions`), whole-body stage physics (`stay`, `hop-bounce`/`double-hop`, `pendulum-drag`, `squash-pop`), prop/FX behaviors (`attach`, `orbit`, `arc-to-landmark`, `bonk-from-edge`, `burst`), and safety-only Go pack validation live in code.
  - *Open asset dictionaries (single `pack.json` per pack):* `poses` (`stand` required, `layers[]`), `gestures` (`replaces[]` slot swaps), `expressions` (`decal` vs Track 1 parametric), `props`, `fx`, `motions`, `hairs`, and `presets` are open maps with `fallback` chains; unknown extension fields pass through untouched so future pack additions remain T0.
  - *Declarative scenario registry:* The 12 canonical scenarios ship as a built-in starter data table rather than hardcoded engine branches; packs can override, disable (`disabled: true`), or add single-beat or multi-step (`steps[]`) scenarios with safe declarative `when` guards purely via `pack.json`, and directors can invoke open scenario IDs or primitive combos with graceful fallback.
- **Zero-cost when `off`:** When `dashboard.companion_enabled` is `false` (the default), the shell creates no canvas, runs no `requestAnimationFrame` loop, fetches no pack assets, and incurs zero runtime overhead.
- **T0 compatibility boundary (`release-compatibility.md`):** All companion settings are scalar string entries in `wsconfig`'s `overrides` map declared with existing `dashboard-config-manifest.json` fields (`v0.50.8` verified T0). Never introduce new top-level JSON members in `config.json` (which `v0.50.8` drops on rewrite) or new manifest struct fields (T3).
- **App-scoped shell mount & rail-bottom default home:** Mount once on the persistent outer shell (`shell.js` / `dashboard.tmpl`), surviving normal session switches, with default home resting on the left session rail bottom divider above `.rws-unreg` / `.rfoot`.
- **Windows AV file-touch discipline (`performance.md`):** Companion pack assets are Type 5 blobs indexed lazily in memory on the first companion pack request and refreshed only on explicit user reload (`POST /api/companion/packs/reload`); daemon boot with `off` mode and steady-state warm HTTP asset hits perform zero pack-store directory scans or disk reads.
- **Public repository IP boundary:** Only IP-clean original Werkschaft default assets and engine/schema code live in git; third-party/community packs live exclusively in local `<config-home>/companions/<pack-id>/`.
  - *Distribution (owner 2026-11-22, (110)=a):* third-party packs reach users only through sources the user adds (`261122-feat-ws-companion-pack-sources`). Werkschaft hosts no third-party pack and runs no curated registry of third-party links.
  - *Base-body exception (owner 2026-11-22, (121)=a, confirmed by (122); reworded for the outfit-baked model by (124)=a and (125)=c):* the authoring scaffold is derived from a local reference image and is tracked as the official authoring scaffold at `ai-docs/assets/companion-pet/scaffold-upright.png` ((130), owner 2026-11-22 20:25): it is never shipped in any pack, and its derivation source and intermediates stay local and git-excluded. Rejected: the earlier local-only rule ((121)=a, (122)); the owner reversed it at (130) after the lead verified by visual comparison that the scaffold keeps none of the source's identifying features (hairstyle, hair colors, accessories, clips, outfit and pose all differ; it is a generic chibi body with a generic bob and face in a plain gray tee and shorts). Shipped outfit-baked assets may carry body regions (skin, hands, legs) that trace back to the scaffold, with every identifying feature removed. Any face or hair on the scaffold is a generic placeholder and is cut off before shipping. No character, product, model, or company name appears in any tracked file or pack metadata. Everything layered on the body (head set, outfit design, props) remains original Werkschaft art.
- **Dev fixture vs. ship art separation:** Engine children (`pack-store`, `shell-engine`) use an IP-clean v3.1 technical fixture so engine verification never blocks on art polish; final shipped art lands exclusively through `261122-chore-ws-companion-official-art-pack` with human visual approval.
