# User Commands v2 — Floating Popover, User CRUD, and Inline Override Execution

## Background

The current session user-command UI renders agent-registered commands as an inline `.d-ucmd` chip bar inside `#composer`, which stays completely hidden until an agent calls `session.register_user_command`. Users cannot register their own reusable commands, cannot inspect the command or working directory before running it, cannot attach an additional prompt to ask the agent to execute or analyze the command, and cannot tweak a command or prompt inline for a one-off run or save the tweak back to the template.

User Commands v2 replaces the inline `.d-ucmd` chip bar with a single always-available composer toolbar icon that opens a borderless dark-tonal floating popover listing both agent-registered (`[에이전트]`) and user-created (`[사용자]`) commands as compact 3-line inline-editable cards. To prevent accidental shell execution, agent turns, or deletions, all three action buttons (`▶` Run Now, `↗` Ask Agent, and `×` Delete) require a 1.5s hold-to-confirm gesture via the shared `WsHoldConfirm` helper, while reversible actions (`💾` Save to Template when dirty, per-line `↺` Revert) remain single-click.

## Decisions

- **Single toolbar icon + floating popover with 3-line inline-editable cards (`(1550)=a`, `(1564)=a`):** Replace the inline `.d-ucmd` chip strip with one always-visible composer icon opening a floating popover supporting user CRUD, dual actions (`▶` Run Now into Exec Job HUD and `↗` Ask Agent), inline one-off command/prompt overrides with per-line `↺` revert, conditional `💾` save-to-template, and `×` deletion.
  - Rejected: keeping the inline `.d-ucmd` chip bar inside `#composer`; separate "편집" button with an expandable override drawer; multi-button labeled action row that wraps to two lines.
- **Visual design language (`(1567)=a`, `(1573)=ok`):** Follow `ai-docs/manuals/dashboard-style.md` (borderless Material tonal surfaces, recessed `#16181c` inputs, `color-mix` hover washes, zero harsh outlines), reuse `hold-confirm.js` (`WsHoldConfirm`, 1500ms), synchronize all 11 `wsi18n` locale tables, and verify via side-by-side capture against `user-commands-v2.html`.
  - Rejected: heavy 1px high-contrast bordered cards, custom duplicate hold-timer logic, or omitting side-by-side visual verification.
- **User-created command persistence scope (`(1569)=a`):** Persist user-created commands (`source: "user"`) at **project-root (`root`) scope** in a dedicated `root_user_commands` table inside `user-commands.db` so they survive session close/restart and appear across every session in the same repository/worktree root (`Reconcile` only inspects and prunes `user_commands`, never touching `root_user_commands`). Keep agent-registered commands (`source: "agent"`) session-scoped `(reply, root)` in `user_commands` as today.
  - Rejected: session-scoped `(reply, root)` lifecycle for user-created commands (option `b`), which would lose user-authored commands whenever a session closes; storing `reply = ""` sentinel rows in `user_commands`.
- **`↗` Ask Agent submission & 1.5s hold-to-confirm on all firing actions (`(1570)=a` + owner directive):**
  - `↗` submits immediately via `POST /s/<replyID>/message` as a structured readable message block (command title, `cwd` when set, fenced shell command block, and optional user prompt text) without modifying or overwriting any active draft in `#composer`.
  - **All three triggering/destructive buttons — `▶` (Run Now), `↗` (Ask Agent), and `×` (Delete) — require a 1.5s hold-to-confirm gesture** (`WsHoldConfirm` in `hold-confirm.js`, preserving its existing release-after-ready semantics: hold 1500ms until `data-hold-state="ready"`, then confirm on `pointerup`/`keyup` release; cancel on early release before 1500ms, pointer leave, `Escape`, or `blur`; live popover header confirmation hint; and gentle reminder toast on quick click via `onStart`/`onReady`/`onCancel` timing or an optional backward-compatible cancel-reason argument). Bare `Enter` inside Line 2 or Line 3 must not bypass hold confirmation (focus the corresponding hold button with a subtle hint instead).
  - Rejected: prefilling `#composer` without sending (`(1570)` option `b`); single-click immediate execution on `▶` or `↗`.
- **SQLite schema extension & Compatibility Tier `T0`/`T1` (`(1571)=a`):** Keep `storeSchemaVersion = 2` in `user-commands.db`, add a separate `root_user_commands` table (`PRIMARY KEY (root, id)`, columns `root, id, label, description, line, prompt, cwd, revision, seq`) for project-root user commands, and add defaulted columns (`prompt TEXT NOT NULL DEFAULT ''`, `cwd TEXT NOT NULL DEFAULT ''`) to `user_commands` via idempotent `ALTER TABLE ... ADD COLUMN` on store open (including when opening an existing `user_version = 2` database). Table membership determines `source` (`root_user_commands` → `"user"`, `user_commands` → `"agent"`), and mutations to both tables advance the shared `meta` revision high-water mark.
  - Source-backed compatibility verdict (`ai-docs/manuals/release-compatibility.md`): **T0** for user commands and **T1** for agent `prompt`/`cwd` columns (patch-safe, no minor bump; T2 caveat only on old-binary delete + re-put of an agent command). Old binaries pass `storeMigrate` (`store.go:117-122`), completely ignore `root_user_commands` during `load()` (`store.go:173`), `Reconcile()` (`registry.go:389-404`, `store.go:227-239`), and `put()` (`store.go:204-207`), read explicit 8 columns from `user_commands` in `load()`, and update only `label, description, line, revision` in `put()`, preserving `prompt` and `cwd`.
  - Rejected: storing `reply = ""` rows in `user_commands` at schema version 2 (old binaries run `reg.Reconcile(runner.CronKnown)` at `cmd/ws-mcp/usercmd.go#L44` where `Runner.CronKnown("")` returns `false` at `internal/wsagent/cron_seams.go#L53-L59`, permanently deleting `reply == ""` rows via `store.delReplies`); bumping `storeSchemaVersion` from `2` to `3`, which triggers `ErrStoreNewer` (`store.go:117-119`) and disables `userCmds` on old binaries (**T3**).
- **Backward-compatible REST & MCP API extension (`(1572)=ok`, Compatibility Tier `T0`):**
  - Extend existing `/s/<replyID>/user-commands/*` routes (all read/mutating/run routes gated by `composerGate` — `TrustedWrite(r)` localhost cookie + loopback peer/host + own `Origin` on writes + live open hosted lead check `svc.Open(replyID)`; extend `composerGate` to recognize `PUT` as a write method on `user-commands` while keeping `composer-exec` `POST`-only):
    - `GET /s/<replyID>/user-commands` — returns merged view of session agent commands `(reply, root)` and project-root user commands, each carrying `id`, `label`, `description`, `line`, `prompt`, `cwd`, `source` (`"agent"` | `"user"`), `revision`.
    - `POST /s/<replyID>/user-commands` — create a user command (`source: "user"`, project-root scoped, server-generated or validated slug `id`, `label`, `line`, optional `prompt`, `cwd`, `description`).
    - `PUT /s/<replyID>/user-commands/<id>` — update template fields (`label`, `line`, `prompt`, `cwd`, optional `description`; disambiguated by optional `source` + `revision`) for either a `[사용자]` or `[에이전트]` command in its existing scope (`source` preserved; `revision` incremented).
    - `POST /s/<replyID>/user-commands/<id>/run` — accept optional JSON body fields `{ "source"?: "agent"|"user", "line"?: string, "cwd"?: string }` alongside `submission_id`, `revision`, `retry`, `token` for one-off inline overrides (falling back to the stored template's `line` and `cwd` when omitted), launching `execjob.ShellLaunch` under `execjob.OriginUser` + `UserApproved = true` into the Exec Job HUD (`.xgroup`). Validate and fence `cwd` synchronously before admitting a submission slot (`(1577)=a`: `execjob.ResolveWorkingDir` + `os.Stat` `IsDir` + symlink containment within the lead's bound worktree root; empty = root; outside-root, symlink-escaped, missing, or non-directory paths rejected with HTTP 400).
    - `POST /s/<replyID>/user-commands/<id>/remove` — keep existing route and allow deleting either a `[사용자]` or `[에이전트]` command from its scope (optional `source`, required `revision`).
    - Keep SSE event `"usercmd"` unchanged; broadcast on all create/update/remove mutations (for root-scoped mutations, notify all active sessions sharing `root`).
  - Extend MCP `session.register_user_command` with optional `prompt` (string) and optional `cwd` (string) — **T0 transparent** for existing callers; `source` is always `"agent"`. Preserve `session.unregister_user_command` unchanged.
  - Rejected: introducing parallel `/user-commands-v2` endpoints or changing required MCP tool parameters.
- **Supersede `261121` closed-body / no-browser-`cwd` restriction on `/run` & worktree-root `cwd` fence (`(1577)=a`):** Explicitly supersede `261121-feat-ws-board-command-slots`'s closed-body / no-browser-`cwd` restriction on `POST /s/<replyID>/user-commands/<id>/run` behind `composerGate` + `execjob.OriginUser` (`env` and credentials remain server-owned), aligning with localhost `!` (`composer-exec`). Fence `cwd` (both template `cwd` on HTTP `POST`/`PUT` and MCP `session.register_user_command`, and one-off `/run` override `cwd`) inside the lead's bound worktree root synchronously **before** admitting a submission slot or saving, pairing `execjob.ResolveWorkingDir` (`internal/execjob/execjob.go#L660-L674`, lexical containment) with synchronous `os.Stat` (`IsDir()`) and symlink-resolved containment (`filepath.EvalSymlinks` within the real worktree root): empty = root; relative or in-root existing directories allowed; outside-root, symlink-escaped, missing, or non-directory paths rejected with HTTP 400 (or MCP validation error) without claiming a submission slot.
  - Rejected: allowing arbitrary absolute `cwd` outside the lead's bound worktree root (weakens the `execjob` worktree fence shared with `exec.shell`); keeping `261121`'s closed-body `/run` and requiring `PUT` before run (drops one-off inline overrides, reversing `(1550)`/`(1564)`).
- **Scope-qualified command identity `(source, id)` (`(1578)`, auto-confirmed technical):** Keep session `(reply, root)` and project-root (`root`) ID namespaces independent and disambiguate HTTP `PUT`/`run`/`remove` via optional `source` (`"agent"` | `"user"`, defaulting to `"agent"` when omitted for T0 backward compatibility with older clients), while keying frontend cards/drafts by `source + ":" + id` and ordering the merged list by registration sequence (`seq`).
  - Rejected: cross-scope global ID uniqueness or silent shadowing (agents in any session can register arbitrary IDs via `session.register_user_command` independently of project-root user commands, so cross-scope uniqueness would cause surprising cross-session registration failures and silent shadowing would make `PUT`/`remove` ambiguous).
- **Revision gate & `composerAdmitSlot` idempotency with inline overrides (`(1579)`, auto-confirmed technical):** Enforce displayed template `revision` matching on `POST /s/<replyID>/user-commands/<id>/run` even when `line`/`cwd` overrides are sent (returning 409 `stale`/`withdrawn` + fresh list if the template changed or was removed), and preserve `bc6fa044`'s ordering point so retries and fenced `submission_id`s answer before command lookup without relaunching. Because a lost-response retry after template withdrawal cannot re-read the template, bind server-side `composerSlot`/`composerKnown` equality to `(source, id, revision)` plus the raw request override presence/values `(hasLine, lineOverride, hasCwd, cwdOverride)` (leveraging template `revision` immutability), and bind browser `sessionStorage` in-flight attempt keys to `(source, id, revision, effectiveLine, effectiveCwd)` so reusing the same `submission_id` for a different override returns 409 and editing an inline draft after a lost response starts a fresh submission rather than retrying the old text.
  - Rejected: skipping template revision matching when overrides are present (would drop withdrawal/change detection on shared fields such as `cwd` or `label` and break `composerAdmitSlot`'s single ordering point).
