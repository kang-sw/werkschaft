# Desktop OS Native STT Backend and Composer Voice Input UX (macOS SFSpeechRecognizer and Windows WinRT)

## Background

`261115-feat-ws-dashboard-external-stt-voice-typing` (now in `.done/`) introduced the common `WsVoiceInput` interface and daemon-mediated external STT providers. To provide zero-cost, low-latency voice typing inside the Werkschaft Tauri v2 desktop app without requiring paid API keys, this ticket adds an OS native speech-to-text backend behind the same `WsVoiceInput` contract (owner decision `04=a`, 2026-11-25).

On 2026-11-28 the owner confirmed `(17)=a` to promote and implement this ticket together with four composer UX decisions that sit on top of the backend: bottom-left mic button, unconfigured-click routing to voice settings, inline real-time voice text inside the composer capsule editor, and spacebar-hold push-to-talk. The same day the owner confirmed `(1817)=a` (superseding `(1816)`): a dedicated "Voice Providers" account section with a Powerline priority bar, a separate voice OpenRouter key with an explicit "use top OpenRouter key" toggle, and a mockup-first review gate for all UI. These share frontend surfaces (`#cvox`, `dashboard-voice.js`, the `WsCapsules` editor, the account settings page) and are therefore planned here rather than as separate tickets.

## Decisions

- **Plug into `WsVoiceInput` (`04=a`):** Expose OS native dictation as a selectable backend (`kind:"native"`) in the same settings/provider switcher and composer UX established by `261115-feat-ws-dashboard-external-stt-voice-typing`. Partial recognition hypotheses stream into the composer and only finalized text is committed at the caret on stop.
- **macOS (`SFSpeechRecognizer` via `objc2`):** Implement a native bridge in `agents-plugin-tool/desktop/src/macos/` using `objc2-speech` / `objc2-av-foundation` (consistent with existing `objc2` + `WKScriptMessageHandler` bridges `werkschaftUpdate`/`werkschaftRecovery`/`werkschaftNotify`), adding `NSSpeechRecognitionUsageDescription` to the desktop `Info.plist` (which already carries `NSMicrophoneUsageDescription`) and preferring on-device recognition (`requiresOnDeviceRecognition`) when available for the requested locale.
- **Windows (WinRT `Windows.Media.SpeechRecognition`):** Implement a native bridge in `agents-plugin-tool/desktop/src/windows.rs` using the pinned `windows = "=0.62.2"` crate over the existing `webview2-com` `add_WebMessageReceived` bridge, checking installed recognizer language availability and surfacing clear actionable status when the required OS language pack or the Windows speech privacy setting (online speech recognition) is disabled. Windows is not claimed to be offline: dictation availability depends on that OS setting.
- **Strict origin & renderer isolation:** Keep `withGlobalTauri: false` and `"no-native-authority"`. Restrict the native STT JS bridge strictly to the pinned local daemon dashboard origin. Browser-only (non-Tauri) sessions hide the native backend option and cleanly fall back to external STT providers.
- **Backend id `native`:** The native backend registers under the id `native`, matching the id already named in the `dashboard.voice_backend` manifest description. The daemon cannot observe the shell bridge, so native availability is decided client-side from the bridge handshake; the daemon only stores and relays the selection and order strings.
- **Voice Providers account section (`1817=a`, 2026-11-28):** `/settings?section=account` gains one "Voice Providers" section listing `OS Native STT (Desktop)` (`native`), `OpenRouter (Voice)` (`openrouter`), `OpenAI API` (`openai_api`), `Groq` (`groq`) and local STT (`local/*`). It lives in a dedicated module pair (`dashboard-settings-voice.js` + CSS) wired from `dashboard-settings-account.js` and `pages.go` (settings scripts and CSS are concatenated into `SettingsScript`/`SettingsCSS` at `agents-plugin-tool/internal/wsdashboard/pages.go#L574-L576`, not listed in `dashboardScriptFiles`), because `dashboard-settings-account.js` is already 1,446 lines; the existing grouped voice-key rows in `dashboard-settings-account.js` (the `voiceState` rows from `261115`) move into the new module so the account file ends net smaller. Visuals follow `ai-docs/manuals/dashboard-style.md` and the approved mockup (see the gate in `## Constraints`).
- **OpenRouter (Voice) key separation and shared-key toggle (`1817=a`):** Having the top LLM/agent `openrouter` key never silently enables paid OpenRouter STT. The OpenRouter (Voice) configuration modal shows a "Use top OpenRouter key" toggle (`상단 OpenRouter 키 사용`) only when the top `openrouter` key is configured. ON: the dedicated voice key input is disabled and the top key is used (explicit voice opt-in). OFF, or no top key: the user enters a dedicated voice-only OpenRouter key.
  - *Technical choices (auto-confirmed):* the dedicated key is a new voice-only `wscred` registry entry `openrouter_voice` (`KindAPIKey`, OpenRouter `BaseURL`, `KeyPrefix: "sk-or-"`, `VoiceOnly: true`), so the `261115` fail-closed rules (refused by `ServeToken`, not admitted by `werkProvider`, omitted from the credential CLI, own group in `/api/account/status`) apply by registry flag alone; the `wscred` registry comment states a new API-key provider is one more entry (`internal/wscred/provider.go`, header and `providers` list). The toggle is a global boolean manifest key `dashboard.voice_openrouter_shared_key` (default false) rather than a credential-store flag, so it follows the `config-settings-ui` catalog/mirror/i18n path like the other `dashboard.voice_*` keys. The voice backend id stays `openrouter`; its daemon-side availability becomes `(shared toggle effective AND top key configured) OR openrouter_voice key configured`, and `POST /api/voice/transcribe` resolves the credential by the same rule. Today availability is `configured[ProviderOpenRouter]` alone (`internal/wsdashboard/voice_routes.go`, the `voiceExternalSpecs` list and `handleVoiceCapabilities`), which is the silent enablement this decision removes.
  - *T0 verdict:* additive registry entry, additive manifest keys, and an availability change that is migrated, not broken: the shared toggle is effective when it is present in the global settings overrides (an explicit OFF counts as set and never falls through), else when the order key is unset and legacy `dashboard.voice_backend == "openrouter"` (an explicit prior opt-in), so existing installs keep working; the first Voice Providers UI save materializes the effective value into the toggle key. No stored credential or setting is rewritten or removed.
  - *Rejected:* reusing the top key implicitly because it is configured (silent paid spend, the case `1816` raised); a separate boolean in `credentials.json` (bypasses the settings catalog and mirror rules).
- **Priority order and runtime resolution (`1817=a`):** An ordered provider list is stored as `dashboard.voice_backend_order`, a whitespace-separated string of backend ids (the manifest supports `string` and `boolean` types and the existing `dashboard.companion_sources` is a whitespace-separated list; no array type is used). Effective order: the stored key if set, else `[dashboard.voice_backend]` when that legacy key is set, else `[native]`. `native` is therefore priority #1 by default on a fresh desktop install and nothing else is implicitly added, so legacy installs behave as before (T0). `GET /api/voice/capabilities` gains an additive `order` array carrying the effective order and keeps `selected` for old frontends (first available daemon-known backend in order, nil when the legacy rule gave none). `#cvox` resolves client-side, because only the browser knows the native bridge: walk `order` left to right and use the first backend that is available in the current environment. In a browser with no native bridge, `native` renders dimmed ("Desktop only") and resolution falls through to the next entry. Saving a provider key in the Voice Providers section appends that provider to the order when absent. Model and language: the resolved backend uses `dashboard.voice_model` only when it is the legacy `voice_backend` (as `resolveVoiceTarget` does today), otherwise that backend's default model; `dashboard.voice_language` stays global, and the native recognizer's locale is `voice_language` when set, else the browser/system locale. A native backend that reports itself unavailable on desktop (missing language pack, disabled speech privacy setting, denied permission) is treated as unavailable for resolution, so `#cvox` falls through the order, and its `reason` is shown on the native row in the Voice Providers section. Rejected: daemon-side resolution (cannot see the bridge); an implicit "first configured external" default (the silent-spend problem).
- **Powerline priority bar (`1817=a`):** Inside the Voice Providers section, configured/active providers render as connected chevron segments left to right (e.g. `[ 1. OS Native ] ▸ [ 2. OpenRouter ] ▸ [ 3. Groq ]`), reorderable by drag and drop and by keyboard left/right, persisting `dashboard.voice_backend_order`. Visual details are fixed by the approved mockup.
- **Lifecycle on hide/minimize/tray teardown (epic `11=a`):** Native capture is a composer foreground interaction. Rust tears down the audio engine and releases mic handles immediately on close-to-tray hide, minimize and tray hide (not only via the page's `ws-page-visibility` signal), then notifies the WebView so the controller drops the lock and span.
- **Composer mic button moves to bottom-left (`17=a`, 2026-11-28):** Move `#cvox` out of `#csend-wrap` (right-bottom) to the bottom-left of the conversation composer in `dashboard.tmpl`. Keep its DOM classes and markup self-contained (no coupling to send-button wrappers) so parallel shell overhauls coexist cleanly.
- **Unconfigured click opens Voice Providers settings (`17=a`, superseded in target by `1817=a`, 2026-11-28):** On secure loopback/HTTPS contexts that pass the `261115` daemon guard (loopback peer/Host/viewer cookie; a LAN HTTP viewer still gets no mic control, the `261115` security invariant), `#cvox` stays visible even when no STT backend is usable. A usable backend (first available entry of the resolved order) -> click starts dictation. No provider in the order is available in the current environment -> click opens `/settings?section=account&provider=voice`, focusing and scrolling to the Voice Providers section; from a framed session it must open the settings modal cleanly through the `shOpen`/`shOpenSettings` path in `dashboard-lifecycle.js`. The `provider` query is already consumed by `dashboard-settings.js` and routed to `account.focus(provider)`, so `focus` gains a `voice` case; the earlier `provider=openrouter` auto-expand plan is dropped. This revises the `261115` rule that the mic control is hidden when no backend is usable; eligibility is the capabilities request succeeding (HTTP 200, including an empty `backends` list), which the daemon already distinguishes from the 404 returned to non-local viewers, so no daemon change is needed for eligibility.
  - *Rejected:* hiding `#cvox` when unconfigured (leaves no discoverable path to set up voice typing); deep-linking to the top OpenRouter key editor (would steer users toward the shared key).
- **Inline real-time voice span inside the composer editor (`17=a`, 2026-11-28):** `#ctext` is backed by `WsCapsules.attach` mounting a `contenteditable` `.wsc-editor`. Stream live partial text directly inside it, at the caret, as a visually distinct "음성 입력 중" span (`[data-voice-span]`, tonal tokens per `ai-docs/manuals/dashboard-style.md`). When `WsCapsules` is absent, fall back to a multi-line `#cvox-cap` capsule. `capsules.js`'s `read()` (the editor-to-text serializer at `agents-plugin-tool/internal/wsdashboard/assets/capsules.js#L317`, whose text syncs to `ctext.value` through the native value setter at `#L285`) must exclude `[data-voice-span]` so unfinalized text never leaks into an accidental send. The same exclusion is required in the other canonical DOM readers of the editor contract, which must stay in agreement: `readEditorDom` in `md-editor.js` (`WsMdEditor`, which `ws-input.js` attaches to the same editor element), and the offset/selection math derived from them. `WsMdEditor` reconciles the editor DOM from text, so the span must survive it: skip reconcile while a voice span is live (the composer is locked then, so there are no concurrent edits) and run one reconcile after the atomic replacement. The composer lock from `261115` stays in force while the span is live. Commit lifecycle: `listening -> refining -> atomic span replacement`, with an optional `postProcess?(rawText) => Promise<string>` hook so a future final post-processing API replaces only that exact voice span; with no hook the raw final text replaces the span at once. Applies to every backend (external SSE partials and native partials); final-only backends show the pulsing placeholder in the span and no partial text. This supersedes the `261115` caret-anchored capsule's render location only; "never commit partial text" is unchanged.
- **Spacebar 0.5 s hold push-to-talk (`17=a`, 2026-11-28):** With focus in the composer editor, holding Space for 500 ms starts dictation; `keyup`, `blur` or `Escape` stops and commits. Preconditions: not during IME composition (`isComposing` / `keyCode === 229`), no modifier keys, no autocomplete/slash menu open, and only when a usable backend exists in the resolved order (unconfigured users' typing is untouched). `e.repeat` spaces are suppressed during the hold window; when the threshold fires, the single space inserted by the initial `keydown` is rolled back before the voice span is inserted at that caret position. A short tap (< 500 ms) types a normal space. Because starting dictation engages the `261115` composer lock, which turns the editor `contenteditable="false"` and can drop focus, release detection uses a document-level `keyup` for Space while the hold is armed or active, and a `blur` caused by the lock itself must not count as a release. The gesture handler coexists with the existing editor keydown handling in `ws-input.js` (which already skips `isComposing`/`keyCode === 229`) rather than replacing it.
- **Module split:** `dashboard-voice.js` is already above the 1,000-line soft limit, so new frontend code goes into cohesive sibling modules (`dashboard-voice-native.js` for the bridge adapter, `dashboard-voice-ptt.js` for the hold gesture and inline span) bundled via `pages.go`, and `dashboard-voice.js` ends net smaller.
- **Compatibility tier: T0 additive.**

After approval the verification of Phases 4 and 5 compares a result capture against the mockup side by side.
- **Manual-specific obligations (manuals declared by `AGENTS.md` `### Implementation Conventions`, listed as `Convention:` lines below):** T0 additive per `release-compatibility.md`; zero audio written to disk and the audio engine and mic handles released immediately on stop, close, hide or minimize per `performance.md`; tonal tokens, no `:has()`, compositor-only animation and `prefers-reduced-motion` per `dashboard-style.md`; the new manifest keys follow `config-settings-ui.md` and `wsflow-mirroring.md` (Phase 2 touches `internal/mcp/testdata`, which also brings in `ws-mcp.md`).
- **Native bridge contract (technical, auto-confirmed):** JS to native over a pinned-origin `WKScriptMessageHandler` / WebView2 message named `werkschaftSpeech` carrying `{op: "status" | "start" | "stop" | "cancel", locale?: string}`; native to JS as a dispatched `ws-native-speech` event whose detail is `{type: "ready" | "partial" | "final" | "error" | "hidden", text?, code?, reason?}` (`ready` answers `status` with availability and an actionable `reason` such as a missing language pack or disabled speech privacy setting; `hidden` is the Rust-side teardown notice). Phase 1 may refine the exact payload while implementing, and records the final contract in its Result; Phase 3 consumes the recorded contract. The handler is registered only for the pinned dashboard origin and ignores messages from any other origin.
- **Bridge frame topology and single owner (technical, auto-confirmed):** Session composers live in same-origin iframes, while every existing desktop bridge is installed in the top frame only (`window === window.top` and pinned origin, see `notify-bridge.js`, `update-bridge.js`, `theme-bridge.js`, `daemon-notice.js` in `assets/`). The speech bridge keeps that posture: the top frame alone talks to native; a framed composer reaches it through a same-origin `postMessage` relay to the top frame, and `ws-native-speech` events (including the `hidden` teardown notice) are broadcast from the top frame down to every live frame. Exactly one recognizer exists in Rust: a second `start` while one is active is refused with an `error` event (`code: "busy"`), matching the single-recorder rule already enforced across frames on `window.top` in `dashboard-voice.js`. The top-frame relay records which frame owns the active session, accepts relay messages only from a same-origin child frame it can identify through `event.source`, and cancels the session when the owning frame unloads or detaches, so a removed frame cannot leave the recognizer and mic held. *Rejected:* widening the JS gate so framed pages call native directly (weakens the top-frame pinned-origin isolation the other bridges keep).
- **Result capture method:** Phases 4 and 5 compare a result capture with the approved mockup. The worker uses the existing headless browser-test harness pattern (`internal/wsdashboard/testdata/*.browser.cjs`) when it can run without a live window; otherwise it reports `needs-capture` to the lead instead of launching a browser, and records which method was used in the Result.

2. **Windows native STT bridge (`agents-plugin-tool/desktop/src/windows.rs`):**

   - `CloseRequested` already hides to tray (`macos::hide_to_tray` / `window.hide()`) without touching native STT, and nothing hooks minimize. 4. **Verification:** `cargo test` in `agents-plugin-tool/desktop/` covering origin gating (pure decision function), session lifecycle teardown (start/stop/cancel/hide state machine), and capability reporting; Windows compilation checks (`GOOS`/target cross-check) and macOS/Windows packaged-app smoke checks listed as manual because delegate and recognizer wiring is not unit-testable.

**Done when:** both bridges and the teardown hooks exist, the pure Rust decision/state-machine tests pass, and the macOS bundle carries `NSSpeechRecognitionUsageDescription`.
